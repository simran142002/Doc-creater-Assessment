Ajaia Docs — Tech Spec

Status as of the code in /ajaia-docs. The backend is built; this page also lists what the prototype needs that it does not yet provide.

What it is

Ajaia Docs is a small collaborative document editor. People sign in as one of a few seeded users, write rich-text documents, import .txt/.md/.docx files, and share a document with a teammate as viewer or editor, with an optional short note. It has three parts: a browser UI (React with the TipTap editor), a Next.js API (route handlers under app/api plus service code in lib/server), and a Postgres database (PGlite files on a developer machine and in tests, Neon in production).

2. Key flows

Autosave with version check

  1. Editor loads the doc and remembers its version (say 4).
  2. After a short pause in typing, browser sends PATCH with content and baseVersion: 4.
  3. Server updates the row only if its version is still 4, then sets version 5.
  4. Browser gets the new version back and shows "Saved".
  5. If someone else saved first (now 5), server answers 409 STALE_VERSION with their current copy.
  6. Browser shows the conflict banner. "Keep mine" re-sends with force: true; "Use theirs" loads the copy from the 409.

Share, then recipient sees a note

  1. Owner opens Share, types an email, picks viewer or editor, adds a note (up to 280 characters).
  2. Browser sends PUT /shares. Server finds the user, saves the row, replies 201 (new) or 200 (updated).
  3. Recipient's dashboard list returns the doc under "shared" with handoffNote and unreadNote: true.
  4. Recipient opens the doc. The open call returns the note with unread: true and marks it seen.

Open doc, catch-up highlights

  1. Browser calls POST /open.
  2. Server finds blocks whose last editor is someone else and whose time is after my last visit.
  3. It returns catchUp: changed block ids, number of removed blocks, who edited how many.
  4. Only then does it record the new "last seen" time.
  5. Editor highlights the changed blocks; prev/next steps through changedIds. First visit returns null (nothing to catch up on).

Import → report → undo: the browser posts a file to /api/import; the server converts it, creates the document immediately and returns {doc, report} (kept / dropped / warnings); the report shows in the editor, and "Undo" is a plain DELETE on the new document.

Backend gaps to build

  1. Dismiss note separately from opening. Today /open marks the note seen. Fix: stop doing that in openDocument and add POST /api/documents/:id/note/seen that sets note_seen_at; "Got it" calls it.
  2. Search titles and text. No endpoint exists. Fix: add optional ?q= to GET /api/documents filtering with ILIKE on title and on the content text.
  3. Freshness line after a title-only save. The title branch of saveDocument updates updatedAt but not last_edited_by, so the line can name the wrong person. Fix: set lastEditedBy in that update.

5. Database

TableIn plain wordsKey columns
usersThe seeded people who can sign in.id, email (unique), name, avatar_hue
documentsOne row per document, including its full body.id, owner_id, title (≤200), content (JSONB), block_meta (JSONB), version, last_edited_by, source (blank/import), updated_at
sharesWho else can open a doc, as viewer or editor, plus the note.(document_id, user_id) key, role, note (≤280), note_seen_at
document_viewsWhen each person last opened each doc; drives catch-up.(user_id, document_id) key, last_seen_at

block_meta maps each top-level block id to a content hash, who last changed it and when. Catch-up is a filter over it, not a text diff.
